## Section 1: Listing and indexing social media contents

The following tasks will guide you as you design and code to produce a data block, embedded in a coverphoto that's escorted with visual art (dare I say motion graphics). This multipurpose image is stored in a public space on social media, and further released to safe-keeping at the time of the Leap second to follow thereafter.

It's the SVG (Scalable Vector Graphics) format that allows for storing inside a block of social media data in XML or JavaScript, in syntax that's native across the World Wide Web. Time-framed between two leap seconds, indexed and validated, social media data in JSON format will bring focus to the real value of change.


### Task 1.1: Querying the APIs for public social media profile data

Be it on Facebook, LinkedIn or Twitter, every mature social media platform out there has a way of querying its data via an API (Application Programming Interface).

First off, a query of LeapGest.com API provides data about the relevant time-frame, a timespan that's determined with previous and the upcoming leap seconds (in check with [Wikipedia's article on Leap second](https://en.wikipedia.org/wiki/Leap_second)). Besides, the service also provides a signed-in user with the timestamp of their most recent participation with the #LeapGest campaign.

Secondly, the list of public social media contents gets stored in memory temporarily for the time of coining the #LeapGest data block from the published contents. Multiple consequent API queries are performed until content's timestamp, essentially time of creation, doesn't exceed time-frame of the previous leap second. If a user has previously participated in a #LeapGest campaign, this time-frame may be extended further until the timestamp of that event.

It is important to emphasize that linked external contents shouldn't get ignored here, as they establish context and sometimes even carry the main message. Being a remarkable element, external links should get queried for metadata, most notably the "title" and "description" fields.

Please note that this case only applies to public contents as published on social media, because external inquiries on private information and their checksums isn't currently available on social media and its APIs. Independent queries of private social media data would produce unexpected results, unsuitable for purposes of data validation (by comparing checksums).

*Refer to documentation of social media platform APIs to query a user's public contents. Data schemas are specific to each platform and the naming should closely follow the original form to maintain consistency, though the exact form will likely slightly differ to resemble interfaces in view on social media and to simplify matters (timestamps, rounded to the minute, flattened data schemas with an optimal number of fields, and a matching character encoding).*


### Task 1.2: Indexing social media contents with a trie object

A trie is a dictionary object that splits keywords into a form that's most suitable for quick retrieval of text suggestions while typing.

Words, contained within this object, are split into distinct characters. Each character stands as a key, containing a further object that stores characters of many words to follow after (until the words are complete). A complete word is determined with use of a special character or better, an array that may store additional data, according to the use case.

For the reason of simplicity, each character that's nested in a trie object should be stored as its lower-case equivalent.

*Create a trie object to optimize matching of keywords against social media contents. Store references to content nodes in arrays at word endings.*


### Task 1.3: Tying in contents with hashtags

At time of creating a data block to store contents in SVG image, publicly available social media contents of various types are printed out to the authoring user. Within scope of topics covered with user-generated content and the custom #LeapGest campaign coverphoto, the user will likely know to describe contents which he or she has authored, using keywords as hashtags in camel case format.

A list of all hashtags, used in contents as published on social media, is extracted and sorted by frequency of use in the relevant time-frame. This precompiled list of hashtags is presented to users.

When inserted, a hashtag is added to the caption of the coverphoto in creation. Next to a hashtag, in parentheses, a total count of matching social media content nodes is printed out.

To query and display contents, hashtags may be inserted in either way, manually by typing, or by ticking checkboxes on the precompiled list of published hashtags. This is how the matching social media contents are listed out and sorted. Accordingly, contents with more than one matching keywords place higher.

Upon trying to enter a hashtag that neither contains any capitalized letters nor generates a keyword match, the user is prompted to re-enter the hashtag by typing it in again in the correct form. A tooltip, containing a guideline and an example hashtag (#LeapGest or else), is presented to instruct users that hashtags should be entered in camel case form.

Hashtags, ordered to reflect frequency of matching keywords, are at the root that the index of contents is based on. A string of text which contains hashtags will be published along with the SVG coverphoto (automated where uploading coverphoto is possible by API).

*Extract hashtags from social media contents and store references to IDs of content nodes. Script an algorithm to extract sequences of words from hashtags (camel case) and match output keywords and phrases against a list of text contents. Prepare it to match occurrences of word sequences in reversed orders, also. Implement a dialogue window with a tooltip and an input field to prompt users to re-enter, upon inserting, the hashtags which contain all small capital letters.*


### Task 1.4: Indexing by the most frequently used keywords

Based on user's choice of hashtags to search for, contents are tested for matching keywords and finally, a list of relevant content nodes is sorted by a derived rank.

Hashtags are ordered in a similar way. Hashtags, which have produced the most results, have the higher score and are first in order to appear in caption text.

*Store hashtags in a sorted array of objects, storing within also the rank for each hashtag. When a hashtag that's entered anew also generates new matching content, the list of hashtags should be sorted once more to reflect the accurate number of occurrences in text contents. For best results in terms of efficiency, keywords and phrases that are derived from hashtags may be stored in a dictionary object, containing references to their origins.*


### Task 1.5: Resolving partial keyword matches with a multi-select dropdown

To find partially matching keywords on the public timeline a multi-select dropdown component is employed. Using a dictionary trie object that indexes all words used in the relevant social media contents, suggestions are listed out while typing in a hashtag that behaves as a search term.

All possible variations of keywords that share a similar root, matching a search term entered in part, are displayed when the count of entered characters reaches 2 or 3. A total number of occurrences is displayed next to a matching word suggestion.

If a user enters a word that produces a singular result then only that one word is subject to query. In other case where multiple words match the search term, all partially matching words apply.

*Integrate a multi-select dropdown component to display keyword matches on change of input value. Make it easier on the user by displaying for each word match the number of occurrences and the increase in count of content nodes. When a new term is entered, the visible effect is the content nodes that bubble up.*


### (Task 1.5: Partial keyword matches with a suffix threshold)

To find partially matching words on the public timeline, a threshold is applied to allow for alternative suffixes to a keyword's root. Threshold is a ratio that denounces the length of the root search term to match against text contents, overlapping, whereas the words in comparison may be of a different length.

A slider component is displayed to the user, prompting a change in threshold value. When in use, this value should be a positive ratio that's smaller than 1. For the purpose of validation, this information should be printed out in the coverphoto's caption, or get submitted to LeapGest.com.

*Develop a threshold algorithm to match input keywords with terms that share a common root to a defined extent, thus allowing a margin for alternating suffixes. Integrate a slider component to modify threshold value and on change, showcase its effect by displaying content nodes that bubble up or vanish.*


### Task 1.6: Indexing matching content nodes

The list of relevant content nodes is assembled in a single array with the following descending orders applied: number of matching keywords, timestamp of creation.

Derived from the state of data, of text contents, timestamps, relative attachment URLs/URIs, and any additional significant fields that are common among API calls and front-end social media interfaces, a unique checksum is calculated for the purpose of data validation.

For automatized data validation to succeed, data types and their placement in a schema require following a strict order and logic. The following rules should always apply:

- objects should be stored in a format that's native to SVG – that's either JSON or XML

- when available, `id` is the first defined term, with the purpose to resolve relations to other content nodes (to be excluded from objects when calculating checksums)

- `type` is the second parameter defined, used to determine the current content node's collection name, as declared with the social media vendor's API documentation

- `{collectionName}_id` is defined when there is another content node that the current content node is related to – key name contains the collection name to which the related content node belongs, while the value signifies it's ID parameter (to be excluded from objects when calculating checksums)

- timestamp fields follow after, exactly as declared by a social media vendor's API (i.e. `createdAt`, `updatedAt`, etc)

- any additional fields follow thereafter, listed in alphabetical order

- before submitting to appropriate checksum algorithms, JSON object should be made as condense as possible (minified)

- `checksum_{type}` should come last in the row of fields

- checksum algorithms' code names should be included within the name of key / field (i.e. `checksum_sha256`)

- all fields are declared with use of lower-case letters, only

*Implement a JSON object that stores various arrays of objects, indexes named after the content node types as declared with social media platform documentation. Any unneeded references within content node objects should be omitted prior to calculating checksums, ignoring also any rank parameters that might be in use for sorting (known as a [Schwartzian transform](https://en.wikipedia.org/wiki/Schwarzian_transform)).*


### Task 1.7: Storing a full copy of key content nodes

User may choose to include a copy of specific content nodes by ticking a checkbox, located next to the content. Text and image contents may be stored directly in SVG (although invisible at first sight).

Alongside the index of contents which contains pure metadata, the more important contents may be stored in full, including text and images.

Text should be stored under a key that matches specifications of social media platform's API. Text, received through the API, has already been properly formatted.

Images may be stored in `<img id={id} src​="data:image/jpeg;base64,{imageBinary}" />` tag, with the appropriate `id` attribute that reflects the ID value of its content node. By default, image should be rendered hidden with `style="display:none"` attribute value.

Videos don't fit the SVG format, but may be archived on a local computer and by other remote means, with its content node and the original file's checksum permanently stored in the JSON data block.

It should be noted to the end user that content nodes, especially text contents which are later edited, won't validate unless they are previously stored in full copy – hey, if it's important, why not store a copy. For edited nodes a diffing algorithm should be employed, comparing previous versions with the current version of contents.

*Implement a tooltip to notify the end user about behavior of validation algorithm in the case of contents that are later edited. Implement a checkbox next to a content node to store a copy of its contents. Whether processing data simultaneously or upon the end of JSON data block creation, the final outcomes should remain the same.*


### Task 1.8: Rendering the current status of data block creation

Hashtags, listed in a coverphoto's caption text, are ordered by the number of matches.

To simplify things, caption text and the status bar should be intertwined at this stage of creating a data block. A shared input component may be implemented to allow for input of tags and display some additional parameters, regarding hashtags and the content nodes.

Additional parameters may be displayed to the user:

- total number of all content nodes, listed in scope of hashtags

- total number of content nodes, to store a full copy of

- number of keyword matches, for each hashtag

- number of matching content nodes, for each hashtag

*Each time a hashtag is added or removed and the list of content nodes is updated, the change should reflect in elements, as displayed. Additionally, storing a copy of a content node should also reflect with a change in the status bar.*

### Task 2.1: Calculating checksums of SVG coverphoto and of the contained JSON object

Individual content nodes and their cryptographic signatures are contained within the coverphoto and are expressed in JavaScript.

It would be deemed inefficient to configure external validation for each content node's cryptographic signature alone and likewise, it would be premature to consider a timeline final and compute a checksum on the whole of its chain.

But there just might be some space in between for the case of #LeapGest data block and the coverphoto. With Leap Gesture, users compile an alternative timeline that's focused on a real purpose and use cryptography to verify the contents and their intentions.

In the days before Leap second, checksums of SVG files and JSON objects are generated with the use of latest RSA algorithm available at time being (based on the largest known prime number).

*Write a smart contract on a blockchain computing platform to immutably store a user's social media credentials and the coverphoto's checksum (of the SVG file in whole, and of contents in distinct JSON objects, minified).*


### Task 2.2: Diffing algorithm and future-proof validation

A full copy of content is required in order to validate any content node in its edited, future version. The end user should get to decide which content nodes he or she might edit in the future, or more generally, which content nodes should be granted a full copy of their contents.

The first version of content, in the sense limited to #LeapGest, requires storing its complete state, whereas the modifications leading to its latter and final versions may be stored as patches to optimize data storage.

The one thing to understand about checksum algorithms is that they produce a hash result in a unidirectional manner. State of content may be validated when processed with the checksum algorithm, but the hash result doesn't imply anything about the input on its own (let alone data consistency).

*On next Leap seconds to follow, the previously stored content nodes should receive attention via automated API calls, to check for changes and to store an additional JSON object – the patch.See "diff-match-patch", a package from Google, to learn more about implementing their diffing algorithm.*


### Task 2.3: Generating a JPEG fail-safe image and returning a blockchain address

LeapGest.com keeps in store coverphotos that are submitted through its service. For the times when SVG isn't the option of choice for a given social media platform, a JPEG image is rendered based on the main SVG version of a coverphoto.

Registrants receive an email with a link to their coverphotos in the last few minutes before the Leap second. As blockchain platforms take more time to write data to their chains, the service will update online resources with block address and notify users on the following day.
